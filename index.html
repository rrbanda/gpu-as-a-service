Why GPUaaS for AI Is Different

The Three Problems

Problem 1: Memory Claimed ≠ Demand Served

Serving frameworks claim GPU memory upfront by configuration, regardless of how much work is arriving. A model reporting 90% GPU memory utilization may be serving zero requests. “The GPUs are full” is usually a setting, not a measure of demand. Enterprise GPU fleets show 30–50% idle rates. Overprovisioning by 300% is common.

Problem 2: Multi-Tenant GPU Sharing Is Unsolved

Traditional Kubernetes treats GPUs as opaque integer counters — nvidia.com/gpu: 1. The scheduler has no awareness of GPU type, memory size, MIG capability, or current utilization. Four teams sharing a cluster have no mechanism for fair-share allocation, quota enforcement, or cost attribution.

Problem 3: Regulated Industries Add Hard Constraints

Air-gapped deployment, audit trails, multi-vendor GPU procurement policies, FIPS compliance, and disconnected operation are non-negotiable for financial services. Many AI infrastructure tools assume cloud connectivity.

How the Platform Addresses Regulatory Constraints
  • FIPS 140-2 validated cryptography — all TLS, certificate, and key management uses FIPS-validated modules
  • Signed OCI artifacts — every container image, Helm chart, and operator bundle is signed with cosign and verified at deploy time
  • Supply chain integrity — SLSA provenance for all Red Hat-built images; SBOM generation for audit
  • Disconnected / air-gapped operation — full mirror registry support; no outbound network required post-install
  • FedRAMP-capable architecture — OpenShift has achieved FedRAMP High authorization; AI services inherit the control plane
  • Dedicated Product Security team — vulnerability scanning, CVE response SLAs, and proactive security advisories

What Makes AI GPUaaS Different From Traditional IaaS

Seven AI-Specific Challenges

1. Wildly Different Workload Shapes

0.25 GPU notebook for 4 hours, 4-GPU fine-tune for 2 hours, 64-GPU training for 3 days, always-on 8-GPU LLM — all at the same time. This is the packing problem.

2. GPUs Are Not Fungible

“8 GPUs” is never a complete request. GPU model, memory (24GB vs 80GB vs 141GB), topology, network (RDMA), precision (FP8/BF16), driver version — all matter.

3. Topology Matters Enormously

8 GPUs on one NVSwitch domain (900 GB/s interconnect) vs 4+4 split across servers connected by network. Same GPU count, dramatically different performance for tensor parallelism.

4. Queues, Quotas, Fairness

100 GPUs, 150 requested. Who gets what, when? This is business policy, not merely a technical scheduler. It requires admission control.

5. Training ≠ Inference

Training

  • Queue jobs
  • Can wait
  • Hours/days
  • Throughput matters
  • Scheduler-oriented

Inference

  • Serve requests
  • Usually can’t wait
  • Persistent
  • Latency/SLO matters
  • Autoscaling/routing-oriented

6. LLM Inference Is Unique

KV cache, prefill vs decode phases, token throughput, TTFT, LoRA adapters, continuous batching. The shift: from “give me 8 H100s” to “deploy Llama at 500 req/sec.”

7. Self-Service Abstractions Needed

Data scientists want “Large Fine-Tuning” not nvidia.com/gpu: 4. The translation layer from human intent to hardware configuration is core infrastructure.

AI-Aware Services
llm-d intelligent routing, WVA autoscaling, KServe model serving
▾

llm-d (CNCF Sandbox, co-created by Red Hat, Google, IBM, CoreWeave, NVIDIA) is distributed inference middleware. Its Endpoint Picker (EPP) routes each request to the replica with the most relevant KV-cache already loaded via a KV-Cache Indexer that maintains a near-real-time block-key-to-pods mapping. llm-d adds three capabilities: (1) KV-cache-aware routing — directs requests to replicas that already have relevant context cached, avoiding redundant computation; (2) Disaggregated prefill/decode — separates compute-intensive prompt processing from memory-intensive token generation across different GPU pools; (3) Tiered prefix caching — reuses shared system prompts and tool definitions across requests, particularly valuable for agentic workloads chaining 10–20 LLM calls. WVA (Workload Variant Autoscaler) scales model replicas based on inference-specific signals: queue depth, KV-cache pressure, token throughput, latency percentiles.

The Centerpiece

Three Control Loops

GPU workload management is not one scheduling problem. It is three problems operating at three different timescales. Conflating them creates oscillation — the autoscaler and the quota manager fight each other.

Three
Timescales

Outer Loop: Kueue — Entitlement

Minutes–hours. Which team is entitled to GPU capacity? Manages quotas, fair-share weights, borrowing, preemption.

Middle Loop: WVA/KEDA — Scaling

Seconds–minutes. How many replicas does this model need? Scales based on queue depth, KV-cache pressure, token throughput, latency.

Inner Loop: llm-d EPP — Routing

Milliseconds. Which replica handles this request? Routes to the replica with the most relevant KV-cache via KV-Cache Indexer.

Insight: Kueue sets the ceiling. WVA scales within it. llm-d routes within the live replicas.

  name: a100-mig-slice
  namespace: content-safety
spec:
  spec:
    devices:
      requests:
      - name: mig
        exactly:
          deviceClassName: mig.nvidia.com
          selectors:
          - cel:
              expression: |
                device.attributes['gpu.nvidia.com'].productName == 'NVIDIA A100 80GB PCIe'
                && device.attributes['gpu.nvidia.com'].profile == '1g.10gb'
Compare with the legacy approach: nvidia.com/gpu: 1 — an opaque integer with no awareness of GPU type, memory, or MIG capability.

Scale-to-Zero: Releasing Idle GPUs

The three mechanisms above improve utilization of active GPUs. Scale-to-zero solves the other half: GPUs reserved by models that aren’t serving any traffic at all.

How it works: KServe provides Knative-based autoscaling including scale-to-zero for model endpoints. When a model receives no inference requests for a configurable idle period, its pods are terminated and GPUs are returned to the cluster. When a new request arrives, KServe cold-starts the model — pulling it from cache (seconds) or downloading weights (minutes).

Combined with KEDA: KEDA watches queue depth and custom inference metrics to trigger scale-up before latency degrades. Together, KServe + KEDA bridge the gap between “no demand” and “auto-scaling to meet demand” without manual GPU reservation.

WVA adds intelligence: WVA’s minReplicas: 0 setting enables scale-to-zero for specific model variants, while optimizing cost by preferring cheaper GPU variants first during scale-up.

Why it matters: Without scale-to-zero, a data science team with 20 deployed models keeps 20+ GPUs reserved even when only 3 models are actively serving. Scale-to-zero recovers 85% of idle capacity automatically.

Kueue Configuration

When Kueue applies — and when it doesn’t. Do not add Kueue merely because GPUs are involved.

Decision Framework

Scenario A: Dedicated Inference Pool

WVA optimizes the pool directly. No multi-tenant contention.

Kueue: NO

Scenario B: Inference + Training Shared

Prevents training from starving production inference.

Kueue: YES

Scenario C: Service-Tier Boundaries

Critical (48 GPUs guaranteed, no preempt) / Standard (32, best-effort, can borrow) / Elastic (16, preemptible, spot-like)

Kueue: YES

GPU FinOps

GPU FinOps — Chargeback

Metering Pipeline

Metering (what consumed?) → Rating (what rate?) → Allocation (who pays?)

Two Core Principles

Charge for allocation, not utilization

Tying billing to utilization makes costs unpredictable and incentivizes gaming — teams run busy loops to look efficient.

Billable share = max(compute share, memory share)

A model using 20% compute but 70% VRAM is billed at 70%.

What Gets Charged vs What Gets Shown

Charge For

  • Allocated GPU-hours (reserved capacity)
  • Burst / borrowing above guaranteed quota
  • Premium priority tier surcharge
  • Dedicated topology reservation (NVLink groups)
  • Token throughput (API-style billing)

Show (Don’t Charge)

  • Queue wait time (scheduler delay)
  • Platform maintenance windows
  • Failed placement attempts
  • Idle allocation visibility (optimization signal)
  • Cross-team borrowing credits returned
Why separate them? Charging for queue wait punishes teams for platform-level capacity gaps. Showing it drives FinOps conversations about fleet sizing. Charging for failed placements creates perverse incentives to avoid experimentation.

The Solution — In Order

Implementation Roadmap

Each step solves a specific problem from the environment above. The order matters — each phase unlocks the next, and early wins build the confidence to tackle harder problems.

Quick Wins — Immediate ROI, Zero Risk
1
Idle GPU Reclamation

Problem solved: 22 notebooks holding GPUs with 0 bytes used

Set NOTEBOOK_CULL_IDLE_TIME on the notebook controller. This is a configuration change — no new operators, no architecture changes. Notebooks idle beyond the threshold (e.g., 60 minutes) are automatically stopped and their GPUs released. Recovers 22 A10G GPUs immediately.

Why first: Zero risk. Zero cost. Immediate measurable result. Builds credibility with leadership before touching production workloads.

Recovers: ~22 GPUs · Effort: 1 day · Risk: None
2
MIG Slicing for Small Models

Problem solved: 14 A100s running 1–3GB guard models at 2.5% VRAM

Enable MIG on A100 nodes via the NVIDIA GPU Operator MIG Manager. Partition each A100 into 7x 1g.10gb slices. Redeploy the 14 content safety models onto MIG slices. 14 full GPUs collapse to 2 GPUs with MIG — freeing 12 A100s back to the fleet.

Why second: Highest dollar-value recovery per unit of effort. MIG is hardware-isolated — no noisy-neighbor risk. Content safety models are non-latency-critical, making them the safest workload to migrate first. Requires NVIDIA GPU Operator (already installed) with MIG Manager enabled.

Recovers: ~12 A100s · Effort: 1–2 weeks · Risk: Low
Foundation — Enable Type-Aware Scheduling
3
DRA Enablement

Problem solved: nvidia.com/gpu: 1 — no GPU type, memory, or MIG awareness

Install the NVIDIA DRA driver alongside the GPU Operator (with legacy device plugin disabled). Label DRA-targeted nodes with nvidia.com/dra-kubelet-plugin=true. Define DeviceClasses for each GPU type (H100, A100, A10G) and MIG profiles. Teams can now request specific GPU types and MIG slices declaratively via ResourceClaimTemplates instead of opaque integers.

Why third: DRA is the foundation for type-aware GPU scheduling. Everything after this step depends on the cluster knowing what kind of GPU a workload needs, not just how many. DRA GA in RHOAI is targeted for 3.6/3.7 (requires OpenShift 4.21+ / Kubernetes 1.34).

Enables: Type-aware GPU claims · Effort: 1–2 weeks · Prereq: OCP 4.21+
Inference Optimization — Make Every GPU Work Harder
4
Inference Optimization with llm-d

Problem solved: LLM replicas serve duplicate context, no KV-cache reuse across requests

Deploy llm-d with the Endpoint Picker (EPP) and KV-Cache Indexer. The EPP routes each request to the replica that already has the most relevant context in its KV-cache. Disaggregated prefill/decode separates prompt processing from token generation. Prefix caching reuses shared system prompts across agentic chains. Combined, these reduce per-request latency and enable higher throughput per GPU.

Why fourth: Now that the cluster knows GPU types (DRA), llm-d can request the right GPUs for inference pools. llm-d makes each GPU work harder — getting more throughput from the same hardware before you need to scale out. Requires RHOAI 3.5+ with Red Hat Connectivity Link and Leader Worker Set operators.

Improves: Inference throughput per GPU · Effort: 2–3 weeks · Prereq: RHOAI 3.5
5
Scale-to-Zero for Inference

Problem solved: 36 H100s reserved overnight serving zero requests

Configure KServe autoscaling with scale-to-zero on model endpoints. Models that receive no traffic for a configurable period (e.g., 15 minutes) release their GPUs entirely. When a new request arrives, KServe cold-starts the model. Pair with KEDA for queue-depth-based scale-up to prevent cold-start latency from reaching users. WVA’s minReplicas: 0 enables variant-level scale-to-zero.

Why fifth: Scale-to-zero is the biggest single GPU recovery — 36 H100s overnight. But it requires KServe and llm-d to be in place so that cold-start is manageable and requests route correctly during scale-up. This is where the fleet starts breathing.

Recovers: ~36 H100s overnight · Effort: 1 week · Prereq: KServe + llm-d
6
Autoscaling for Bursty APIs

Problem solved: GenAI platform provisioned for peak (16 A100s), averages 25% utilization

Deploy KEDA (Custom Metrics Autoscaler) with WVA for inference-aware scaling. KEDA watches queue depth and WVA’s wva_desired_replicas metric. API endpoints scale from 2 replicas at trough to 12 at market open — automatically. No manual provisioning for peak.

Why sixth: Autoscaling amplifies scale-to-zero. Together they create a fully elastic inference layer: zero at night, minimal at trough, scaled at peak. KEDA GA for llm-d is targeted in RHOAI 3.6. Requires KEDA operator + User Workload Monitoring for Prometheus metrics.

Recovers: ~12 A100s (peak-to-avg gap) · Effort: 1–2 weeks · Prereq: KEDA + monitoring
Governance — Sharing, Fairness, Cost Visibility
7
Fair-Share Governance with Kueue

Problem solved: Training jobs saturate the cluster weekly, inference latency spikes 10x

Install the Red Hat build of Kueue Operator. Define ResourceFlavors for each GPU type. Create ClusterQueues with guaranteed quotas for inference (high priority, no preemption) and training (lower priority, can borrow from inference when idle, preemptible). Configure cohort-level borrowing so idle inference GPUs flow to training automatically, but reclaim instantly when inference demand returns.

Why seventh: Now that inference is elastic (steps 4–6), there are regularly idle GPUs to share. Kueue makes that sharing safe. Without elastic inference first, there’s nothing to share — every GPU is statically claimed. Set Kueue to Unmanaged in the DataScienceCluster CR so the standalone Kueue Operator manages scheduling.

Solves: Training/inference contention · Effort: 2–3 weeks · Prereq: RH build of Kueue
8
GPU FinOps — Metering & Showback

Problem solved: Nobody knows what their GPU usage costs

Enable DCGM Exporter for GPU telemetry. Configure Kueue GPU credit transformations to normalize heterogeneous GPU types (H100 = 100 credits, A100 = 60, MIG slice = 10). Build showback dashboards showing each team’s allocated cost, active compute, and idle waste. Start with visibility — teams change behavior when they can see their cost.

Why eighth: FinOps requires Kueue (for credit normalization) and DCGM (for utilization metrics). Both must be in place first. Start with showback, not chargeback — let 1–2 quarters of data build trust before enforcing billing.

Enables: Cost visibility · Effort: 2 weeks · Prereq: Kueue + DCGM
Scale — Training, Self-Service, Multi-Cluster
9
Distributed Training with KubeRay

Problem solved: Training jobs are ad-hoc, no orchestration for multi-node GPU workloads

Enable the Ray component in the DataScienceCluster CR. Data scientists submit RayJob or RayCluster specs for fine-tuning, hyperparameter sweeps, and distributed training. KubeRay manages multi-node GPU scheduling, auto-scales worker pools, and integrates with Kueue for fair-share admission. Training workloads run in Kueue-governed queues with borrowing from idle inference capacity.

Why ninth: Training orchestration depends on Kueue for admission control and fair sharing. Without Kueue, training jobs compete in a free-for-all. Set ray: Managed and trainingoperator: Managed in the DataScienceCluster CR.

Enables: Governed distributed training · Effort: 1–2 weeks · Prereq: Kueue + RHOAI
10
Self-Service & Multi-Cluster

Problem solved: GPU access via ServiceNow ticket (3–5 day turnaround) + no cross-cluster visibility

Deploy Accelerator Profiles (available now) and Compute Profiles (targeted RHOAI 3.7) so data scientists select GPU sizes from the RHOAI dashboard — no YAML, no tickets. Deploy Red Hat ACM for fleet-wide GPU visibility, policy-based workload placement, and GitOps-driven configuration consistency across production, staging, and dev clusters. Transition from showback to chargeback once data has built organizational trust.

Why last: Self-service requires all the guardrails to be in place first — Kueue quotas, DRA type-awareness, MIG slicing, cost visibility. Without them, self-service means uncontrolled GPU consumption. ACM extends the single-cluster wins across the fleet.

Enables: Self-service + fleet management · Effort: 3–4 weeks · Prereq: All above
The logic of the order: Steps 1–2 are zero-risk quick wins that recover GPUs immediately and build organizational confidence. Step 3 (DRA) is the foundation every later step depends on. Steps 4–6 make inference elastic, creating idle capacity to share. Step 7 (Kueue) makes that sharing safe and fair. Step 8 makes the value visible. Steps 9–10 open the platform to everyone — but only after the guardrails are in place.
