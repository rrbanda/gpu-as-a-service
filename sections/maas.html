Layer 5 Deep Dive — AI Workload Surface

Models-as-a-Service & GenAI Studio

GPU infrastructure exists to serve AI workloads. MaaS provides governed access to LLMs with token quotas and API key management. GenAI Studio adds discovery, playground, and agentic tool orchestration.

MaaS Governance Model (GA in RHOAI 3.4)

API Request → MaaSAuthPolicy (model access) → MaaSSubscription (token quota) → Rate Limit Check → Inference Server

MaaSSubscription

Defines per-group token quotas with rate limiting. Each subscription specifies which models a group can access, with configurable windows (per hour, per day) and maximum token counts. Enables showback by tracking consumption per subscription.

MaaSAuthPolicy

Controls which groups can access which models, independent of quota. Combined with subscription-based quotas, this provides fine-grained access control: Team A can use Llama-3 with 100K tokens/hour; Team B cannot access Llama-3 at all.

MaaSSubscription — team token quota with rate limiting 
apiVersion: maas.opendatahub.io/v1alpha1
kind: MaaSSubscription
metadata:
  name: team-a-premium
  namespace: models-as-a-service
spec:
  owners:
  - kind: Group
    name: team-a
  models:
  - name: llama-3-70b
    namespace: model-serving
    rateLimits:
    - window: 1h
      maxTokens: 100000
  - name: qwen3-8b
    namespace: model-serving
    rateLimits:
    - window: 24h
      maxTokens: 1000000

GenAI Studio

AI Hub

Centralized discovery of models, tools, and MCP servers. Browse, search, and deploy models from a curated catalog.

Playground

Interactive, stateless environment for prompt testing and parameter tuning. Compare model outputs side by side.

MCP Catalog & Gateway

Curated catalog of MCP servers with lifecycle operator for declarative deployment. MCP Gateway provides identity-aware routing and per-tool metrics for agentic workflows.

llm-d — Disaggregated Inference

llm-d (CNCF Sandbox) separates compute-intensive prefill from latency-sensitive decode, enabling independent scaling and hardware optimization.

Request → Gateway → EPP Router → Prefill Pool → KV Cache Transfer (NIXL) → Decode Pool
LLMInferenceService — single CR for model deployment with llm-d 
apiVersion: serving.kserve.io/v1alpha1
kind: LLMInferenceService
metadata:
  name: qwen3-8b
spec:
  replicas: 2
  model:
    uri: hf://RedHatAI/Qwen3-8B-FP8-dynamic
    name: RedHatAI/Qwen3-8B-FP8-dynamic
  router:
    route: {}
    gateway: {}
    scheduler: {}
  template:
    containers:
    - name: main
      resources:
        limits:
          nvidia.com/gpu: "1"
          memory: 32Gi
Key insight: llm-d’s EPP checks existing KV-cache state in each replica before routing. For agentic workloads chaining 10–20 LLM calls with shared system prompts, prefix caching avoids redundant computation across requests.
