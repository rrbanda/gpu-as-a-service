What Makes AI GPUaaS Different From Traditional IaaS

Seven AI-Specific Challenges

1. Wildly Different Workload Shapes

0.25 GPU notebook for 4 hours, 4-GPU fine-tune for 2 hours, 64-GPU training for 3 days, always-on 8-GPU LLM — all at the same time. This is the packing problem.

2. GPUs Are Not Fungible

“8 GPUs” is never a complete request. GPU model, memory size (24 GB vs 80 GB vs 141 GB), connection speed, and driver version all matter. Asking for “a GPU” is like booking “a room” without specifying bed size or floor.

3. Topology Matters Enormously

8 GPUs on one machine (connected at 900 GB/s) vs 4+4 split across two servers connected by slower network. Same GPU count, dramatically different performance.

4. Queues, Quotas, Fairness

100 GPUs, 150 requested. Who gets what, when? This is business policy, not merely a technical scheduler. It requires admission control.

5. Training ≠ Inference

Training

  • Queue jobs
  • Can wait
  • Hours/days
  • Throughput matters
  • Scheduler-oriented

Inference

  • Serve requests
  • Usually can’t wait
  • Persistent
  • Latency/SLO matters
  • Autoscaling/routing-oriented

6. LLM Inference Is Unique

Large language models have performance characteristics that generic autoscalers can’t handle. The shift: from “give me 8 GPUs” to “deploy Llama at 500 requests/sec.”

Technical details

KV cache management, prefill vs decode phases, token throughput, time-to-first-token (TTFT), LoRA adapter routing, and continuous batching all require inference-aware scheduling.

7. Self-Service Abstractions Needed

Data scientists want “Large Fine-Tuning” not nvidia.com/gpu: 4. The translation layer from human intent to hardware configuration is core infrastructure.
