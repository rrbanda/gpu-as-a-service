GPU FinOps — Chargeback

⚡ Think: your electricity bill — you see exactly how many kilowatt-hours each department consumed, when peak usage happened, and what it cost. Start by showing the bill (showback). Enforce payment (chargeback) once everyone trusts the numbers.

Metering Pipeline

Metering (what consumed?) → Rating (what rate?) → Allocation (who pays?)

Two Core Principles

Charge for allocation, not utilization

Tying billing to utilization makes costs unpredictable and incentivizes gaming — teams run busy loops to look efficient.

Billable share = max(compute share, memory share)

A model using 20% compute but 70% VRAM is billed at 70%.

What Gets Charged vs What Gets Shown

Charge For

  • Allocated GPU-hours (reserved capacity)
  • Burst / borrowing above guaranteed quota
  • Premium priority tier surcharge
  • Dedicated topology reservation (NVLink groups)
  • Token throughput (API-style billing)

Show (Don’t Charge)

  • Queue wait time (scheduler delay)
  • Platform maintenance windows
  • Failed placement attempts
  • Idle allocation visibility (optimization signal)
  • Cross-team borrowing credits returned
Why separate them? Charging for queue wait punishes teams for platform-level capacity gaps. Showing it drives FinOps conversations about fleet sizing. Charging for failed placements creates perverse incentives to avoid experimentation.

FOCUS Specification

FOCUS v1.4 (FinOps Open Cost and Usage Specification) standardizes billing datasets across cloud and Kubernetes environments. Key for GPU chargeback: provides a common schema for GPU-hours, resource attribution, and multi-vendor cost normalization. Version 1.5 will add AI token-level cost breakdown — essential for MaaS billing.

Implementation path: Start with 90-day showback → enforce label taxonomy (app.kubernetes.io/name, team, cost-centre) via OPA Gatekeeper → correlate DCGM metrics with K8s metadata → graduate to chargeback once data is trusted.
