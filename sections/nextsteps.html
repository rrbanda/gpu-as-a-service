The Solution — In Order

Implementation Roadmap

Each step solves a specific problem from the environment above. The order matters — each phase unlocks the next, and early wins build the confidence to tackle harder problems.

Quick Wins — Immediate ROI, Zero Risk
1
Idle GPU Reclamation

Problem solved: 22 notebooks holding GPUs with 0 bytes used

Set NOTEBOOK_CULL_IDLE_TIME on the notebook controller. This is a configuration change — no new operators, no architecture changes. Notebooks idle beyond the threshold (e.g., 60 minutes) are automatically stopped and their GPUs released. Recovers 22 A10G GPUs immediately.

Why first: Zero risk. Zero cost. Immediate measurable result. Builds credibility with leadership before touching production workloads.

Recovers: ~22 GPUs · Effort: 1 day · Risk: None
2
MIG Slicing for Small Models

Problem solved: 14 A100s running 1–3GB guard models at 2.5% VRAM

Enable MIG on A100 nodes via the NVIDIA GPU Operator MIG Manager. Partition each A100 into 7x 1g.10gb slices. Redeploy the 14 content safety models onto MIG slices. 14 full GPUs collapse to 2 GPUs with MIG — freeing 12 A100s back to the fleet.

Why second: Highest dollar-value recovery per unit of effort. MIG is hardware-isolated — no noisy-neighbor risk. Content safety models are non-latency-critical, making them the safest workload to migrate first. Requires NVIDIA GPU Operator (already installed) with MIG Manager enabled.

Recovers: ~12 A100s · Effort: 1–2 weeks · Risk: Low
Foundation — Enable Type-Aware Scheduling
3
DRA Enablement

Problem solved: nvidia.com/gpu: 1 — no GPU type, memory, or MIG awareness

Install the NVIDIA DRA driver alongside the GPU Operator (with legacy device plugin disabled). Label DRA-targeted nodes with nvidia.com/dra-kubelet-plugin=true. Define DeviceClasses for each GPU type (H100, A100, A10G) and MIG profiles. Teams can now request specific GPU types and MIG slices declaratively via ResourceClaimTemplates instead of opaque integers.

Why third: DRA is the foundation for type-aware GPU scheduling. Everything after this step depends on the cluster knowing what kind of GPU a workload needs, not just how many. DRA GA in RHOAI is targeted for 3.6/3.7 (requires OpenShift 4.21+ / Kubernetes 1.34).

Enables: Type-aware GPU claims · Effort: 1–2 weeks · Prereq: OCP 4.21+
Inference Optimization — Make Every GPU Work Harder
4
Inference Optimization with llm-d

Problem solved: LLM replicas serve duplicate context, no KV-cache reuse across requests

Deploy llm-d with the Endpoint Picker (EPP) and KV-Cache Indexer. The EPP routes each request to the replica that already has the most relevant context in its KV-cache. Disaggregated prefill/decode separates prompt processing from token generation. Prefix caching reuses shared system prompts across agentic chains. Combined, these reduce per-request latency and enable higher throughput per GPU.

Why fourth: Now that the cluster knows GPU types (DRA), llm-d can request the right GPUs for inference pools. llm-d makes each GPU work harder — getting more throughput from the same hardware before you need to scale out. Requires RHOAI 3.5+ with Red Hat Connectivity Link and Leader Worker Set operators.

Improves: Inference throughput per GPU · Effort: 2–3 weeks · Prereq: RHOAI 3.5
5
Scale-to-Zero for Inference

Problem solved: 36 H100s reserved overnight serving zero requests

Configure KServe autoscaling with scale-to-zero on model endpoints. Models that receive no traffic for a configurable period (e.g., 15 minutes) release their GPUs entirely. When a new request arrives, KServe cold-starts the model. Pair with KEDA for queue-depth-based scale-up to prevent cold-start latency from reaching users. WVA’s minReplicas: 0 enables variant-level scale-to-zero.

Why fifth: Scale-to-zero is the biggest single GPU recovery — 36 H100s overnight. But it requires KServe and llm-d to be in place so that cold-start is manageable and requests route correctly during scale-up. This is where the fleet starts breathing.

Recovers: ~36 H100s overnight · Effort: 1 week · Prereq: KServe + llm-d
6
Autoscaling for Bursty APIs

Problem solved: GenAI platform provisioned for peak (16 A100s), averages 25% utilization

Deploy KEDA (Custom Metrics Autoscaler) with WVA for inference-aware scaling. KEDA watches queue depth and WVA’s wva_desired_replicas metric. API endpoints scale from 2 replicas at trough to 12 at market open — automatically. No manual provisioning for peak.

Why sixth: Autoscaling amplifies scale-to-zero. Together they create a fully elastic inference layer: zero at night, minimal at trough, scaled at peak. KEDA GA for llm-d is targeted in RHOAI 3.6. Requires KEDA operator + User Workload Monitoring for Prometheus metrics.

Recovers: ~12 A100s (peak-to-avg gap) · Effort: 1–2 weeks · Prereq: KEDA + monitoring
Governance — Sharing, Fairness, Cost Visibility
7
Fair-Share Governance with Kueue

Problem solved: Training jobs saturate the cluster weekly, inference latency spikes 10x

Install the Red Hat build of Kueue Operator. Define ResourceFlavors for each GPU type. Create ClusterQueues with guaranteed quotas for inference (high priority, no preemption) and training (lower priority, can borrow from inference when idle, preemptible). Configure cohort-level borrowing so idle inference GPUs flow to training automatically, but reclaim instantly when inference demand returns.

Why seventh: Now that inference is elastic (steps 4–6), there are regularly idle GPUs to share. Kueue makes that sharing safe. Without elastic inference first, there’s nothing to share — every GPU is statically claimed. Set Kueue to Unmanaged in the DataScienceCluster CR so the standalone Kueue Operator manages scheduling.

Solves: Training/inference contention · Effort: 2–3 weeks · Prereq: RH build of Kueue
8
GPU FinOps — Metering & Showback

Problem solved: Nobody knows what their GPU usage costs

Enable DCGM Exporter for GPU telemetry. Configure Kueue GPU credit transformations to normalize heterogeneous GPU types (H100 = 100 credits, A100 = 60, MIG slice = 10). Build showback dashboards showing each team’s allocated cost, active compute, and idle waste. Start with visibility — teams change behavior when they can see their cost.

Why eighth: FinOps requires Kueue (for credit normalization) and DCGM (for utilization metrics). Both must be in place first. Start with showback, not chargeback — let 1–2 quarters of data build trust before enforcing billing.

Enables: Cost visibility · Effort: 2 weeks · Prereq: Kueue + DCGM
Scale — Training, Self-Service, Multi-Cluster
9
KubeRay: Training + Ray Serve Inference

Problem solved: Training jobs are ad-hoc; multi-model inference needs built-in autoscaling

Enable the Ray component in the DataScienceCluster CR. For training: submit RayJob or RayCluster specs for fine-tuning, hyperparameter sweeps, and distributed training. KubeRay manages multi-node GPU scheduling, auto-scales worker pools, and integrates with Kueue for fair-share admission. For inference: Ray Serve wraps vLLM with 3-tier autoscaling — application-level replicas scale on target_ongoing_requests, the Ray Autoscaler adjusts worker pods, and the cluster autoscaler provisions GPU nodes. Multiple models share a single RayService cluster with independent scaling policies.

Why ninth: Training orchestration depends on Kueue for admission control and fair sharing. Ray Serve inference is an alternative to KServe+llm-d for teams that need multi-node tensor-parallel serving or multi-model multiplexing from a single cluster. Set ray: Managed in the DataScienceCluster CR.

Enables: Governed distributed training · Effort: 1–2 weeks · Prereq: Kueue + RHOAI
10
Self-Service & Multi-Cluster

Problem solved: GPU access via ServiceNow ticket (3–5 day turnaround) + no cross-cluster visibility

Deploy Accelerator Profiles (available now) and Compute Profiles (targeted RHOAI 3.7) so data scientists select GPU sizes from the RHOAI dashboard — no YAML, no tickets. Deploy Red Hat ACM for fleet-wide GPU visibility, policy-based workload placement, and GitOps-driven configuration consistency across production, staging, and dev clusters. Transition from showback to chargeback once data has built organizational trust.

Why last: Self-service requires all the guardrails to be in place first — Kueue quotas, DRA type-awareness, MIG slicing, cost visibility. Without them, self-service means uncontrolled GPU consumption. ACM extends the single-cluster wins across the fleet.

Enables: Self-service + fleet management · Effort: 3–4 weeks · Prereq: All above
The logic of the order: Steps 1–2 are zero-risk quick wins that recover GPUs immediately and build organizational confidence. Step 3 (DRA) is the foundation every later step depends on. Steps 4–6 make inference elastic, creating idle capacity to share. Step 7 (Kueue) makes that sharing safe and fair. Step 8 makes the value visible. Steps 9–10 open the platform to everyone — but only after the guardrails are in place.
