Key insight: The left path (Prod Reservation) is latency-sensitive — llm-d routes in milliseconds, WVA scales in seconds. The right path (Elastic Pool) is throughput-oriented — Kueue queues jobs for minutes to hours and allows borrowing from idle production capacity.

Pattern Variations

Pattern A: Dedicated Inference Pool

Request Traffic → llm-d EPP (ms) → WVA (sec-min) → kube-scheduler → GPU Pool (inference only)
Note: No Kueue in the path. WVA distributes capacity across models directly. Simpler, lower latency.

Pattern B: Shared Cluster

GPU Pool (128 H100s) → Kueue Governance → Inference Pool (60% quota, WVA + llm-d)
GPU Pool (128 H100s) → Kueue Governance → Training Pool (40% quota, batch jobs)
Note: Kueue prevents training from starving inference. WVA operates freely inside the inference envelope.

Why Not Just KubeRay?

Ray Serve is an excellent inference engine. In 2026, it supports prefix-aware routing (consistent hashing), disaggregated prefill/decode, and multi-LoRA multiplexing with LRU eviction. For a single team serving models on dedicated GPUs, it may be all you need. The gap emerges at the platform level.

Enterprise problemWhat Ray Serve doesWhat’s needed beyond it
Request routing Consistent hashing for session affinity; prefix-aware routing via session_id llm-d EPP — precise KV-cache indexing via real-time model server events (ZeroMQ), modular scorer pipeline (prefix + load + latency + LoRA-affinity), deep Kubernetes Gateway API integration
Prefill/decode disaggregation Supported — Ray Serve LLM handles P/D with similar TTFT improvements llm-d + NIXL — zero-copy GPU-to-GPU KV transfer via RDMA (IB, RoCE, EFA). Bidirectional D→P pull for multi-turn reuse. Production-grade on OpenShift with InferencePool CRD
Multi-tenant GPU quotas Not addressed — Ray manages one cluster for one team Kueue — fair-share quotas, borrowing, preemption, priority classes across 4+ teams sharing a GPU fleet
GPU partitioning Not addressed — allocates whole GPUs per replica MIG + DRA — carve one A100 into 7 isolated slices for small models (guard rails, embeddings). Hardware-isolated, no noisy neighbors
Cost attribution No concept of GPU credits or showback FinOps layer — DCGM telemetry + Kueue GPU credit normalization + showback/chargeback dashboards
Self-service abstractions Requires YAML (RayService manifests, serveConfigV2) Compute Profiles — data scientists pick “Small GPU” from a dropdown; the platform maps it to the right GPU type, MIG profile, and queue
Air-gapped & regulated Assumes network access for image pulls, model downloads OpenShift — disconnected mirror registries, FIPS 140-2 crypto, signed OCI artifacts, FedRAMP-capable control plane
Multi-cluster orchestration Single-cluster only ACM — policy-based workload placement, fleet-wide GPU visibility, GitOps across clusters
When Ray Serve IS the right choice: You need multi-node tensor parallelism (model too large for one node). You want to serve many fine-tuned LoRA variants from a shared replica pool (dynamic_lora_loading_path with LRU eviction, max_num_adapters_per_replica). Your team already uses Ray for training and wants a unified platform. In these cases, KubeRay + Kueue is a strong combination — Ray handles the inference/training plane, Kueue governs the capacity.
