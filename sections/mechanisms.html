DRA Resource Claim (Dynamic Resource Allocation) — GA in OCP 4.21 / K8s 1.34

DRA replaces nvidia.com/gpu: 1 with attribute-based CEL expressions. Drivers publish device attributes via ResourceSlice. Users request devices via ResourceClaim with selectors for GPU model, memory, architecture, and MIG profile. DeviceClass defines device categories. DRA supports partitionable devices (dynamic MIG without pre-config), device taints (mark degraded hardware), and shared counters (prevent overlapping MIG allocations).

ResourceClaimTemplate — requesting a MIG slice by GPU type and profile 
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: a100-mig-slice
  namespace: content-safety
spec:
  spec:
    devices:
      requests:
      - name: mig
        exactly:
          deviceClassName: mig.nvidia.com
          selectors:
          - cel:
              expression: |
                device.attributes['gpu.nvidia.com'].productName == 'NVIDIA A100 80GB PCIe'
                && device.attributes['gpu.nvidia.com'].profile == '1g.10gb'
ResourceClaimTemplate — requesting a Hopper GPU with 80GB+ memory 
apiVersion: resource.k8s.io/v1
kind: ResourceClaimTemplate
metadata:
  name: hopper-gpu
  namespace: llm-serving
spec:
  spec:
    devices:
      requests:
      - name: gpu
        exactly:
          deviceClassName: gpu.nvidia.com
          selectors:
          - cel:
              expression: |
                device.attributes['gpu.nvidia.com'].architecture == 'Hopper'
                && device.capacity['gpu.nvidia.com'].memory.isGreaterThan(quantity("80Gi"))
Compare with the legacy approach: nvidia.com/gpu: 1 — an opaque integer with no awareness of GPU type, memory, or MIG capability.

Scale-to-Zero: Releasing Idle GPUs

MIG and DRA improve utilization of active GPUs. Scale-to-zero solves the other half: GPUs reserved by models that aren’t serving any traffic at all.

⚡ Think: the electricity meter stops when you turn off the lights — and starts instantly when you flip the switch. You pay only for power you actually consume.

How it works: KServe provides Knative-based autoscaling including scale-to-zero for model endpoints. When a model receives no inference requests for a configurable idle period, its pods are terminated and GPUs are returned to the cluster. When a new request arrives, KServe cold-starts the model — pulling it from cache (seconds) or downloading weights (minutes).

Combined with KEDA: KEDA watches queue depth and custom inference metrics to trigger scale-up before latency degrades. Together, KServe + KEDA bridge the gap between “no demand” and “auto-scaling to meet demand” without manual GPU reservation.

WVA adds intelligence: WVA’s minReplicas: 0 setting enables scale-to-zero for specific model variants, while optimizing cost by preferring cheaper GPU variants first during scale-up.

Why it matters: Without scale-to-zero, a data science team with 20 deployed models keeps 20+ GPUs reserved even when only 3 models are actively serving. Scale-to-zero recovers 85% of idle capacity automatically.

Faster Model Loading: Making Scale-to-Zero Practical

Scale-to-zero only works if cold-start is fast. A 70B model downloading weights from object storage takes 5–30 minutes — unacceptable for production. The solution is a layered approach to storage and loading.

Shared Storage (NAS / PVC)

Download once, infer everywhere. Store model weights on a ReadWriteMany (RWX) persistent volume — NFS, GPFS, or Lustre. New pods mount the same volume and load weights directly into GPU memory. The download step is eliminated entirely.

Pattern: An init container checks if the cache is warm. If yes, it exits immediately. If not, it downloads the model once. All subsequent replicas skip the download. KServe + RHOAI model registry supports pvc:// URIs for this pattern.

Accelerated Loading (vLLM)

Even from fast storage, default sequential loading leaves 80% of bandwidth unused. vLLM supports multiple accelerated loaders:

  • Run:ai Model Streamer — concurrent multi-threaded reads of safetensors, streaming directly to GPU memory (--load-format runai_streamer)
  • CoreWeave Tensorizer — custom serialization that bypasses CPU staging, loads 40–50% faster than safetensors (--load-format tensorizer)
  • Prefetch mode — pre-warms OS page cache in background threads while workers parse tensors (--safetensors-load-strategy prefetch)
  • Torch compile cache — set VLLM_CACHE_ROOT to persistent storage to avoid recompilation on restart
Combined impact: Shared NAS + accelerated loader reduces cold-start from 5–30 minutes to 30–90 seconds for a 70B model. This makes scale-to-zero viable even for latency-sensitive endpoints.
