DEEP DIVE — AGENT POD

Layer 1: Agent pod anatomy — supervisor, sandbox, three nested defense rings

Why PID 1 matters: the supervisor sets up the world before the agent even starts

  • Boot sequence: supervisor starts first, fetches policy, installs kernel filters, injects SPIFFE credentials — then launches the harness as a child process
  • Every outbound connection passes through the supervisor's egress proxy — default posture is deny-all, allowlist per endpoint
  • This is where Tier 1 routing lives: the security decision about whether data may leave the cluster happens here, not at the model level
  • PII masking for external endpoints also lives here — detection-and-redaction at the proxy before any data exits
  • Honest limitation: PII masking is heuristic — false negatives are the failure mode, so monitor for residual leakage
  • In-cluster inference also enters through the governed front door (AI Gateway), not direct to vLLM pods

DEEP DIVE — SUPERVISOR / EGRESS PROXY

Defense in depth: three rings and four cross-cutting controls

Three concentric rings plus four cross-cutting controls. Each ring assumes the ring inside it has already failed.

OpenShell + Kata: neither alone covers the full threat surface

OpenShell (Application + Identity Layer)

  • Kernel isolation via Landlock + seccomp + network namespaces
  • Per-binary, per-path, per-endpoint, MCP-aware L7 policy
  • Cannot stop kernel exploits — shares host kernel with agent
  • Adding: SPIFFE identity, OCSF audit, inference routing

Kata Containers (VM Layer)

  • Isolates kernel exploits — dedicated VM with own kernel
  • virtiofs blocks page-cache attacks
  • Cannot filter network traffic — curl is normal userspace
  • No mechanism to inspect or block outbound data

Run both: the dual-protected pod is the only configuration that stops both attack classes

  • OpenShell catches prompt injection exfiltration — egress proxy blocks unauthorized network calls
  • Kata contains kernel exploits — dedicated VM with its own kernel, virtiofs blocks page-cache attacks
  • Neither alone is sufficient: OpenShell cannot stop kernel exploits, Kata cannot filter network traffic
  • The dual-protected pod (OpenShell inside Kata) is the only empirically validated safe configuration
  • We will prove this with benchmark results later in the session
DEEP DIVE — FLOWS AND ROUTING

Layer 3: Three routing tiers — security, cost, efficiency — with different owners

Three routing tiers: WHERE may this go, WHICH model, WHICH replica — different owners, different change cadences.

Why three tiers instead of one — each answers to a different team and changes at a different speed

Internal vs External flows: Tier 1 decides where data may travel — confidential context never leaves the cluster

Internal Flow (In-Cluster)

  • Confidential context stays on in-cluster models
  • Traffic enters through the AI Gateway (governed front door)
  • Tier 2 picks the model, Tier 3 picks the replica
  • Full OpenTelemetry trace within the cluster
  • No PII masking needed — data stays within trust boundary

External Flow (Cloud / SaaS)

  • Tier 1 supervisor egress router decides: may this leave?
  • PII detection-and-redaction at the proxy before any data exits
  • Masked request routed to external LLM endpoint
  • Failure mode: false-negative leakage — must be monitored
  • Optional: external endpoint entirely blocked by policy

DEEP DIVE — MCP GATEWAY

Layer 2: MCP Gateway — claims-based tool authorization, not prompt-based

Walk through the attack: injected prompt tries to call an unauthorized tool — what happens?

Being honest about what the gateway cannot stop — and what picks up the slack

  • The gateway stops unauthorized tool calls. It cannot stop misuse of tools the agent IS entitled to use
  • Example: the agent is allowed to call a database API — an injection makes it exfiltrate data through that permitted endpoint
  • That gap is covered by other layers: inference guardrails (TrustyAI, NeMo) screen I/O at the model boundary, EvalHub provides continuous quality and safety scoring, and egress policy limits where data can flow
  • This is why the architecture has multiple overlapping controls — no single checkpoint is the whole defense
  • Every team deploying this should explicitly map which control covers which threat class in their environment

DEEP DIVE — AUTH BRIDGE + IDENTITY

Layer 4: SPIFFE identity eliminates static keys — leaked workspace has nothing durable to steal

Deep dive: Auth Bridge — the token exchange most teams overlook

Before vs After: static keys replaced by per-agent cryptographic identity

Before — Static Keys

  • API keys in environment variables
  • Rotated quarterly (maybe)
  • One key = full access to all tools
  • Leaked prompt = leaked key = game over
  • No per-agent granularity
  • Revocation = redeploy everything

After — SPIFFE + Claims

  • Cryptographic identity at pod level
  • Auto-rotated, short-lived (5 min)
  • Per-agent tool entitlements via claims
  • Leaked workspace = nothing durable to steal
  • Per-agent, per-namespace granularity
  • Revocation = revoke one identity, one operation

What is not solved yet — and where you should plan ahead rather than wait

  • Identity chaining: when an agent delegates to a shared runtime, does its per-agent identity survive downstream? Today it does not
  • The IETF WIMSE working group is building the standard for this — track it, but do not assume it in your 2026 design
  • Identity convergence: OpenShell is adding SPIFFE JWT-SVID grants and OAuth2 exchange alongside its kernel isolation — converging sandbox and identity into one platform (Dev/Tech Preview targeted for RHOAI 3.5/3.6)
  • Practical advice: deploy SPIFFE/SPIRE and Auth Bridge today with manual configuration — OpenShell will be a drop-in convergence when ready
DEEP DIVE — LOOP PLACEMENT

Layer 5: Agent-as-a-Workload vs Agent-as-a-Service — trade-off matrix

Agent-as-a-Workload

  • Loop ships inside the pod with the harness
  • Own identity (SPIFFE SVID per pod)
  • Own blast radius (sandbox contains failure)
  • Long-running, autonomous workloads
  • Harnesses: OpenClaw, LangGraph, Custom

Agent-as-a-Service

  • Loop runs in shared runtime (OGX, Responses API)
  • Centralized audit trail across tenants
  • Credential isolation (clients never hold tool creds)
  • Request-scoped assistants and copilots
  • RHOAI 3.5 Early Access

The two patterns compose: sandboxed pod delegates to shared loop while keeping its own identity

  • A sandboxed agent pod can delegate tool execution to a shared OGX loop
  • The agent keeps its own identity and its own defense rings
  • The MCP Gateway preserves per-agent policy inside the shared runtime
  • Start with Agent-as-a-Workload for autonomous, long-running agents
  • Use Agent-as-a-Service for request-scoped assistants and copilots
  • The same governance (identity + tool auth) works across both
PATTERN — MULTI-AGENT ISOLATION

The supervisor pattern: one brain orchestrates, each agent runs in its own sandbox with its own policy

Per-agent network policy via OpenShell. When the agent finishes, its sandbox is destroyed — no state leaks.

PROOF

Benchmark: 3 pods, 2 attacks — only dual protection stopped both

Where does vendor gravity actually live — and how does this architecture contain it?

  • The lock-in audit most teams skip: it is not the model layer (swappable behind standard APIs) — it is the skill libraries and the silicon
  • CUDA-X (cuDF, cuOpt, PhysicsNeMo) and NIM containers only run on NVIDIA — that is real gravity
  • What the architecture gives you: every skill backend sits behind a neutral MCP/REST interface with a policy envelope
  • Swapping cuOpt for OR-Tools is a gateway policy update and an endpoint change — the agent code and the rest of the stack never notice
  • The design rule: choose NVIDIA (or AMD, or Intel) per component, per use case — never as a structural dependency across the architecture

Decision framework: when to use Agent-as-a-Workload versus Agent-as-a-Service

QuestionIf Yes → WorkloadIf Yes → Service
Does the agent run for hours or days?Long-lived = own pod, own identity
Does it make autonomous decisions?Own blast radius is critical
Is it request-scoped (one user, one task)?Shared runtime amortizes overhead
Do you need centralized audit across tenants?Loop runtime captures every step
Do clients need to stay credential-free?Clients never hold tool credentials
Can you tolerate shared blast radius?Single point of failure is acceptable

Most teams start with Workload for autonomous agents and add Service for copilots later. The governance layer is identical in both.

What this architecture does NOT require — clearing up common misconceptions

  • Does NOT require NVIDIA hardware — vLLM runs on CUDA, ROCm, XPU, and CPU; the inference path is silicon-independent
  • Does NOT require rewriting your agents — BYOA (Bring Your Own Agent); existing harnesses (LangGraph, LangChain, custom) work; governance wraps around them
  • Does NOT require all components at once — each layer is independently deployable and provides incremental security value
  • Does NOT require a specific model — any model behind OpenAI-compatible API works; swap models without touching the architecture
  • Does NOT require waiting for preview features — the mature column (SPIFFE, Kata, vLLM, llm-d, Envoy) is production-ready today
  • Does NOT lock you to Red Hat — every interface is open; the architecture runs on any conformant Kubernetes cluster
